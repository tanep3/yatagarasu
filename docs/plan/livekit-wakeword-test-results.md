# LiveKit WakeWord 実機試験結果

- 実施日: 2026-07-28
- 実施環境: TaneMini、第8世代Core i7、GPUなし
- 音声入力: Tapoカメラ -> go2rtc RTSP、16kHz mono、80msチャンク
- 対象モデル: `models/wakeword/nee_yatagarasu.onnx`
- CPU指標: LinuxプロセスCPU、1論理CPUを100%として算出

## 1. 確定設定

```env
LISTEND_WAKE_THRESHOLD="0.65"
LISTEND_WAKE_EARLY_THRESHOLD="0.15"
LISTEND_WAKE_EARLY_CONSECUTIVE="3"
LISTEND_WAKE_ACTIVE_INTERVAL_SEC="0.08"
LISTEND_WAKE_IDLE_INTERVAL_SEC="1.5"
LISTEND_WAKE_ACTIVITY_RMS_DBFS="-50"
LISTEND_WAKE_SPEECH_HOLD_SEC="2.0"
LISTEND_WAKE_WARMUP_SEC="0.0"
```

実機の正例には`0.1757 -> 0.1611 -> 0.1524`のような低score系列があり、
早期閾値`0.50`では検出できなかった。通常閾値`0.65`と
早期閾値`0.15`の3回連続を実機受入値とした。

## 2. CPU負荷

各測定はservice起動後に60秒ウォームアップし、その後300秒測定した。
listend本体の`/proc/<pid>/stat`に記録されたCPU時間と`/proc/uptime`を使用した。

| 条件 | 平均CPU | ONNX推論回数 | drop | timeout / fatal / reconnect |
|---|---:|---:|---:|---:|
| STT互換、ONNX無効 | 7.34% | 0 | 0 | 0 / 0 / 0 |
| ONNX、80ms scheduler | 15.29% | 399 | 0 | 0 / 0 / 0 |
| ONNX、CPU低減候補 | 11.35% | 179 | 0 | 0 / 0 / 0 |

80ms schedulerの追加CPU使用率は`15.29 - 7.34 = 7.95` percentage pointsで、
目標の5 percentage pointsを満たしていない。
CPU低減候補は4.01ポイントまで抑えたが、実機の正例を取りこぼしたため不採用とした。
CPU測定時の閾値は`0.70 / 0.50`だったが、閾値判定はONNX推論後の定数時間処理であり、
推論間隔が同じ現在設定のCPU負荷を代表できる。誤検出評価には流用しない。

測定環境には生活音があり、STT基準測定中にラジオ由来とみられる文字起こしが
1回発生した。発話2回を含んだ先行基準測定は7.54%だった。両測定の差から
文字起こし負荷を除外すると、実機受入設定のONNX増分はさらに大きくなる可能性がある。
推論回数はheartbeatに記録された測定区間内の差分である。

### 2.1 speech embedding再利用

2026-07-29に、連続する80ms音声窓のspeech embedding再利用を実装した。
実モデルへ連続する32窓を入力し、各窓を従来の全再計算結果と比較した。

| 条件 | 初回 | 2回目以降の平均 | p95 | 従来の全再計算平均 |
|---|---:|---:|---:|---:|
| ONNX 1 thread | 57.67ms | 7.48ms | 8.03ms | 56.54ms |

16個中15個のembeddingを再利用する連続窓は、全窓で従来スコアと完全一致した。
音声が不連続な場合は全再計算へ戻る回帰テストも追加した。

同じ再利用方式でONNX Runtimeのthread数を比較した結果、1 threadは平均7.34ms、
2 threadsは5.33ms、4 threadsは11.75msだった。4 threadsは同期とCPU競合の負担が
上回ったため採用しない。thread数はsession生成時の設定であり、VAD状態ごとの動的な
切替にはsessionの複製または再生成が必要となる。得られる短縮量に対して複雑さが
大きいため、現行の1 threadを維持する。

### 2.2 ウェイク遅延trace

2026-07-29に、activity開始からtapovoice送信処理完了までを同一trace IDで計測した。
初回の実発話は次の結果となった。

| 区間 | 時間 |
|---|---:|
| VAD activity開始 -> 検出対象音声窓 | 1906.0ms |
| 最初のcandidate -> 検出対象音声窓 | 113.8ms |
| 音声窓取得 -> 推論完了 | 26.6ms |
| 推論完了 -> main loop受領 | 69.5ms |
| 検出受領 -> prompt process起動 | 13.8ms |
| prompt process起動 -> tapovoice送信処理完了 | 487.9ms |
| VAD activity開始 -> tapovoice送信処理完了 | 2503.7ms |

ONNX推論処理より、モデルが検出可能な時系列へ到達するまでの時間と、
tapovoice/go2rtc送信処理が支配的だった。次段階では、無音先読みを判定に使わず
shadow評価し、短縮可能時間と誤検出リスクを測定する。その後、prompt送信経路の
常駐化を検討する。

追加の実発話2回では、activity開始から検出対象窓までが1071.1msと2027.4ms、
activity開始からtapovoice送信処理完了までが1496.5msと2634.1msだった。
前者は早期判定、後者は通常判定であり、モデル反応時刻に約1秒の差がある。
同条件の推論時間は8.5msと8.4msで、embedding再利用が実運用でも機能している。

1秒の仮想無音を追加するshadow推論は、実モデルで平均60.89ms、p95 76.38msだった。
音声活動終了時に一度だけ実行するため、80ms周期の通常推論へ常時追加しない。

初期shadow運転では、仮想スコア生成から実検出までの経過時間だけを記録した。
これは仮想スコアが実際の1秒後を再現した証拠にはならないため、短縮効果の
受入値には使用しない。実験を修正し、仮想無音を1秒へ固定したうえで、
時刻`t`の仮想スコアと`t+1秒`の通常推論スコアを直接照合する。
音声活動終了後160msで一度だけ計算し、実判定には使用しない。

shadow実験中、prompt送信完了から682ms後にONへ入り、その後「パッ」という
短音をSTTが命令として認識した。仮想無音処理はONNX入力配列だけを操作し、
RTSP/STT bufferへ書き込まない。prompt MP3は1.008秒で、go2rtc送信完了と
Tapo実再生開始が一致しないため、「はい」の遅延回り込みと判断した。
prompt guardを0.6秒から0.8秒へ延長し、命令冒頭を失わない範囲で
WAKING中の破棄時間を確保した。

### 2.3 サンプル基準の無音補完

2026-07-29に、VADで発話終了を確認した時点で2秒窓の不足分を仮想無音で補完し、
実時間の2秒経過を待たずONNX判定するactive先読みを実装した。
補完量は処理遅延の影響を受ける壁時計ではなく、16kHz音声のサンプル数から算出する。

VAD起点は補完済み窓のscoreが`0.55`以上なら検出する。VADなしで通常scoreの
上昇から先読みする場合は、現在scoreが`0.10`以上かつ補完scoreが`0.55`以上を
必要とする。VAD補完要求と未受領結果は通常推論より優先して保持する。

最終修正後、所有者が連続5回発話した結果は次のとおり。

| 回 | activity開始から検出 | prompt送信完了 | 補完score | 起点 |
|---|---:|---:|---:|---|
| 1 | 0.82秒 | 1.33秒 | 0.5796 | VAD |
| 2 | 1.06秒 | 1.56秒 | 0.8566 | VAD |
| 3 | 0.84秒 | 1.34秒 | 0.6219 | VAD |
| 4 | 1.37秒 | 1.77秒 | 0.6376 | score |
| 5 | 1.06秒 | 1.48秒 | 0.8010 | score |

先読み成功率は`5 / 5`、平均検出時間は約`1.03秒`、
activity開始からprompt送信完了までは平均約`1.50秒`だった。
従来の通常検出時に観測した約`2.6〜2.9秒`から約`1.2〜1.4秒`短縮した。
試験直後の短い非ウェイク音声に対する補完scoreは`0.0022`で、誤検出しなかった。

## 3. 機能受入

| 項目 | 結果 | 確認内容 |
|---|---|---|
| ONNX認識 | 合格 | 所有者による約30回の実発話で30回検出 |
| 即時応答 | 合格 | active先読み5回中5回成功、prompt送信完了まで平均約1.50秒 |
| 命令認識 | 合格 | 「はい」後の「右を向いて」を実行 |
| 回り込み防止 | 合格 | 「はい」を命令としてdispatchしない |
| 応答音声ループ防止 | 合格 | dispatch完了後にOFFへ戻り、蓄積した自己音声を破棄。実機で再dispatchなし |
| 無指示キャンセル | 合格 | 3秒後に発話せずOFFへ復帰 |
| STT互換 | 合格 | 「マイカメラ、右を向いて」でON遷移し、右移動を実行 |
| 誤検出 | 制約付き合格 | ラジオ環境では運用可能。音響的に近い語句の誤検出は既知の制約 |

STT互換試験で、日本語読点をCSV区切りとして扱うと
`ねぇ、ヤタガラス`が`ねぇ`と`ヤタガラス`へ分割される問題を検出した。
設定値の区切りをASCIIカンマだけに限定して修正した。

ReazonSpeechは「ねぇ、ヤタガラス」を安定して完全一致へ文字起こしできなかった。
一般文に近い誤認識をエイリアス化すると誤起動を増やすため採用していない。
STT方式は従来ウェイク語を互換用途で使用し、標準の
「ねぇ、ヤタガラス」検出にはONNX方式を使用する。

## 4. 残存確認

### 4.1 音響的に近い呼びかけ

最終設定で、次の誤検出を確認した。

| 発話 | VAD補完score | 通常score | 通常閾値 | 結果 |
|---|---:|---:|---:|---|
| ねぇ、カメラくん | 0.1037 | 0.8440 | 0.65 | 誤検出 |
| ねぇ、山田くん | 0.0194 | 0.6587 | 0.65 | 誤検出 |

同条件の正例「ねぇ、ヤタガラス」の通常scoreは`0.7741`であり、
「ねぇ、カメラくん」のscoreより低い。したがって通常閾値の引き上げだけでは
正例と誤検出を分離できない。応答速度を維持するためSTTによる二段階確認は採用せず、
同梱ONNXモデルの既知の制約としてプロジェクト所有者が受け入れた。

### 4.2 継続監視

確定閾値へ変更した後の連続8時間試験は再実施していない。
通常運用ログで誤検出を継続監視し、発生した場合はscoreと音声環境を記録する。

STT/ONNX切替試験でserviceを繰り返し再起動した後、RTSP接続は継続しているのに
実音声が届かず、ONNX scoreが`0.002`前後へ張り付く事象を確認した。
直接録音にも呼びかけが記録されず、`go2rtc`と`yatagarasu`を順に再起動すると復旧した。
復旧後は実発話2回を2回とも検出した。

LLM dispatchが同期実行されている間もffmpegはRTSP音声を蓄積するため、
dispatch後も`ON`を維持すると、カメラスピーカーからの応答音声を新しい命令として
文字起こしし、自己対話ループになる事象を確認した。1ウェイク1命令へ変更し、
dispatch完了時の`OFF`遷移とRTSP音声consumerの即時リセットを実装した。
最終回帰テストは`python/tests`の全72件が合格した。
`yatagarasu doctor`はLiveKit WakeWord runtime、同梱ONNXとprompt、
CPUExecutionProvider、smoke inference、Hoshikage、VOICEVOX、go2rtc、
user systemd serviceを確認し、fail 0件だった。
実機では天気質問への70.21秒のdispatch後に`OFF`へ遷移し、
RTSP音声consumerをリセットした。その後3分以上、自己音声の文字起こしと
再dispatchが発生しないことを確認した。
